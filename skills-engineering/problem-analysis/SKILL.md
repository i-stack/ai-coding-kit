# Problem Analysis

## 强制入口

命中本 skill 时，**必须先完整阅读** [references/problem_analysis.md](references/problem_analysis.md) 并按其中条款执行。

- 不得以 preamble 或摘要代替该文件全文。
- 规则 ID 真值索引见 [references/rule_index.md](references/rule_index.md)。

## 三条核心规则

- [PA-001] **逻辑检验**：收到问题后，先审查问题本身是否含逻辑错误、矛盾前提、循环假设或虚假二分。若发现，须先揭示，不得在错误前提上直接作答。
- [PA-002] **第一性原理**：推理/取舍类从底层需求拆解——实际要解决的是什么？当前提出的路径是否最优？事实类（API、数字、接口行为、事件）走查证，不从第一性原理推导（与 GR-013 同边界）。若存在更优解或更深层需求，必须在正式回复前点明。
- [PA-003] **理解门控**：PA-001 + PA-002 完成前不开始正式回复。三态：问题清晰且路径合理 → 静默（不输出分析块）；实质逻辑错误、强假设或更优路径 → 输出 `问题分析` 块后作答；底层需求与表层请求不一致 → 先确认真实意图，确认前不推进方案。

细则见 [references/problem_analysis.md](references/problem_analysis.md)。

## `问题分析` 块（机械格式）

仅在显式模式输出。字段名固定，不得改成「逻辑问题 / 更优路径」等别名：

```
问题分析
逻辑检验：<发现的逻辑缺陷，或「无」>
真实需求：<第一性原理拆解后的底层目标>
路径评估：<当前方案是否最优；若有更优解，一句话说明>
```

块后紧接正式回复。本块谈输入（问题本身），不与 `逻辑链` / `验证锚点` / 四段式合并。

## 何时加载

- **默认**：收到任何含判断的技术问题、方案讨论、实现请求、架构取舍时。不依赖用户说出「第一性原理 / 深层需求 / 问题偏差」。
- **跳过**：纯机械执行（格式化代码、直接翻译）、无判断成分的信息复述。
